# PGWhite 1.41 — Initial Atomic Tag Library

**Date:** 2026-10-04  
**Status:** Research Tag Library delivered. **STOP before Qwen3-Embedding and production taxonomy migration.**  
**Version naming:** numeric only (`1.41`). No letter suffixes (not 1.4A / 1.4B).

## Goal

Build the first structured PGWhite Atomic Tag Library that will later support local Qwen3 embedding-based existing-tag retrieval.

This version is about the **Tag Library and research infrastructure**, not production annotation throughput.

Out of scope for 1.41:

- production embedding retrieval
- GPT-5.4 per Quote
- 102-Quote annotation benchmark run
- Community publication behavior changes
- classifier / reranker
- bulk production `tags` migration

## Atomic Tag philosophy

A PGWhite Tag is:

> a semantically atomic, reusable retrieval component

Tags are **not** miniature literary analyses or Quote-specific summaries.

| Prefer | Avoid |
|--------|--------|
| 记忆 / 童年 / 亲情 / 死亡 / 恐惧 / 遗憾 | 音乐唤醒记忆 / 记忆与损伤 / 复杂的父子关系 / 珍视之物的脆弱 |

**High recall > strict precision** for automated suggestion. Occasional extra Personal tags are acceptable because users can review/edit later. The pipeline does **not** currently need a second classifier to prove every retrieved tag is correct.

Authoritative principle doc: `docs/research/1.4-atomic-reusable-tags.md`.

## Why expand taxonomy before embedding evaluation

Existing production Theme inventory is sparse (~13 Themes, many ≤2 assignments). Embedding reconcile against a tiny, skewed basis cannot fairly test retrieval quality: most free concepts will fall through to Personal concepts for the wrong reason (missing basis), not because the embedding failed.

1.41 therefore constructs a trustworthy research basis **first**. 1.42 can then evaluate Qwen3-Embedding representations (A/B/C) against that basis without pretending the current production Theme table is already adequate.

## Canonical vs aliases vs related

These remain **structurally different**:

| Field | Role | Example for `悲伤` |
|-------|------|-------------------|
| **Canonical** | Stable retrieval atom | 悲伤 |
| **Aliases** | Near-synonym / wording variants for deterministic matching | 伤心、难过、哀伤 |
| **Related** | Adjacent but **not** synonymous concepts | 失去、遗憾、孤独 |

Do **not** treat related concepts as synonyms.  
Representation **C** includes aliases and **excludes** related concepts on purpose — so 1.42 can test whether aliases help retrieval without contaminating the vector with adjacency.

## Abstraction boundary

Prefer reusable literary concepts over enumerating every concrete entity, relation subtype, event subtype, or wording variation.

Example: a Quote about a father dying may map toward `亲情` + `死亡` + `失去` + `悲伤`.

We do **not** automatically create a separate canonical Theme for every family member. A small number of highly reusable relationship roles (`父亲` / `母亲` / `孩子`) may remain if independently useful for retrieval.

Do not mechanically collapse everything into ultra-broad concepts either.

## Empty Tags are acceptable

The initial library may contain concepts that currently match **zero** PGWhite Quotes. Empty Tags are still useful as:

- retrieval basis candidates for future Quotes
- targets for free-concept reconcile experiments
- documentation of intended semantic coverage

## Generative AI for one-time taxonomy construction

Using a strong model **offline** to help construct a one-time candidate library is acceptable and encouraged.

This is **fundamentally different** from calling GPT-5.4 for every imported Quote:

| One-time taxonomy construction | Per-Quote ingestion |
|--------------------------------|---------------------|
| Builds reusable basis | Labels individual Quotes |
| Inspectable, editable research artifact | Recurring cost/latency |
| Suggestions, not literary authority | Should prefer retrieve-existing over invent-new once basis is strong |

Generated candidates are recorded with provenance `generated_candidate`.

LTO is a **research/reference** source. 1.41 inspects hierarchy and extracts useful upper / early-middle concepts; it does **not** blindly import ~2990 themes into production.

## Device library (conservative)

Smaller Device pass prefers conventional reusable literary terminology (e.g. family of 比喻 / 隐喻 / 拟人 / 排比 / 反讽 / 象征 / 通感 / 夸张 / 白描 / 借代).

Invented analysis-title Devices from Nano calibration (e.g. `拟因果的环境指向`, `对称/均分结构`) are excluded unless external evidence establishes them as reusable terminology. Cleanup decisions are logged.

## Definition quality

Definitions describe the Tag’s **semantic territory** for future embedding retrieval. They should be concise and reusable — not Quote-specific explanations, and not stuffed with every related concept.

## Representations for future embedding (not computed yet)

For each Tag:

- **A** — label only: `记忆`
- **B** — label + definition: `记忆：…`
- **C** — label + definition + aliases (related excluded)

Embeddings are **not** run in 1.41. Text forms live in `research/tag-library/data/library/representations.v1.json`.

## Fourier / basis analogy (conceptual only)

A Quote can conceptually be decomposed into reusable semantic basis components (Tags), possibly with different relevance strengths.

**Do not claim** PGWhite uses Fourier Transform, frequency-domain processing, DSP, or FFT. This is a product/conceptual analogy for “basis components,” nothing more.
