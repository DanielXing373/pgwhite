# AC1 结果归档（2026-11-12）

自动标注内部竞赛三轮的分数汇总。方案和命令见上一级的 `README.md`。

本目录的文件：

| 文件 | 内容 |
| --- | --- |
| `holdout60-final.report.md` / `.json` | holdout60 上 4 个配置的三档计分（`scripts/score.mjs --unjudged acceptable`） |
| `dev58-final.report.md` / `.json` | dev58 上 15 个来源的两档计分（`scripts/score.mjs`，默认模式） |

`.json` 里有每个组合、每个维度的全部计数、比例、分位置数字和 Wilson 95% 区间，写作引用数字时以它为准。两份报告都可以用上一级 `README.md` 里的计分命令从 `runs/` 和 `packs/` 重新生成。

模型原始输出在 `runs/`，盲审包和判定文件在 `packs/`，两者都被 `.gitignore` 忽略，只在本机。**判定文件是人工成果，无法重新生成，注意自行备份。**

## 一句话结论

- 整库进 prompt、20 条一批、三个维度合并调用，是成本最低且质量不输的写法。
- 在验证集 holdout60 上，DeepSeek Flash（不推理）的明显错误最少，Luna 低档、中档推理紧随其后，三者差距在误差内；Luna 不推理最差。
- 所有配置的成本都在每万条 ¥4–11，远低于“几十元”的红线。
- 全部结论来自 58 + 60 条摘抄、单人盲审，样本小，只能看方向。

## 怎么读这些数字

两个数据集的判定方式不同，**数字不能跨数据集比较**。

| | dev58（开发集） | holdout60（验证集） |
| --- | --- | --- |
| 判定档位 | 两档：合适 / 不合适 | 三档：合适 / 可接受 / 明显错误 |
| 未判的标签 | 前两次导出按“不合适”补齐，第三次全部明确判定 | 算“可接受”（留在库里不会删） |
| 盲审包 | 分 3 次增量判定，后两次只显示新出现的标签 | 一次判完，每段显示全部候选 |
| 偏向 | 偏悲观：漏看的标签被算成错 | 更接近真实使用 |
| 用途 | 调 prompt、调标签库 | 只用于最终排名，不据此改任何东西 |

指标：

- **认可率 / 合适率**：该配置给出的标签里被判合适的比例。
- **明显错误率**（仅 holdout60）：被明确打叉的比例。用户默认不审查标注结果，所以这是首要指标。
- **覆盖率**：所有被判合适的标签里，该配置给出了多少。它相对于当次参赛配置的合并标签池，不是绝对召回率。
- **元/万条**：按价目表和实际 token 估算，不是账单。DeepSeek 按高峰价计。

误差：每个配置每个维度只有几十到两百个标签。两百个标签时认可率的误差约 ±7 个百分点，三四十个标签时约 ±15 个百分点。

### 明显错误集中在哪

- 动作描写：5 条摘抄被错标，是错得最多的单个标签（只是提到动作，不是描写动作）。
- 比喻 3 条，欲望 2 条（“想要”不等于欲望）。
- holdout-006、holdout-060 两条各有 4–5 个错标签，四个配置都在这两条上出错。

### 建议的前三名

DeepSeek Flash 不推理、Luna 低档推理、Luna 中档推理。Luna 不推理淘汰。三者之间的差距（6% 对 8%，相当于 4–5 个标签）在误差内，不能断言谁更好。只选一个的话倾向 Flash：错误最少、最快、成本可接受。**这是建议，是否定为前三由项目负责人决定。**

## 开发集各轮：dev58

以下认可率、覆盖率来自 `dev58-final.report.md`，按最终的合并标签池（15 个来源、700 个标签、3 份判定）统一重算，所以和每轮当时汇报的数字略有出入。

### 第 1 轮：候选范围 × 每次条数 × 证据（只做主题，Luna 不推理，prompt v1）

| 配置 | 认可率 | 覆盖率 | 第 1 / 2 / 3 个认可率 | 标签数 | 元/万条 |
| --- | ---: | ---: | --- | ---: | ---: |
| 整库 逐条 无证据 | 66.0% | 58.7% | 82.8 / 74.1 / 51.0 | 200 | 5.21 |
| 整库 20 条 无证据 | 60.6% | 57.3% | 81.0 / 65.5 / 41.1 | 213 | 2.11 |
| 整库 逐条 带证据 | 63.0% | 50.7% | 81.0 / 66.1 / 48.8 | 181 | 6.25 |
| 整库 20 条 带证据 | 61.9% | 49.8% | 82.8 / 56.9 / 51.1 | 181 | 2.75 |
| Top20 逐条 无证据 | 64.6% | 52.0% | 75.9 / 70.9 / 55.8 | 181 | 11.22 |
| Top20 逐条 带证据 | 67.7% | 46.7% | 75.9 / 67.3 / 62.9 | 155 | 12.55 |

基线（同一批判定）：

| 来源 | 认可率 | 覆盖率 | 标签数 | 元/万条 |
| --- | ---: | ---: | ---: | ---: |
| 人工标注 | 84.3% | 43.1% | 115 | — |
| EL2 旧版 Luna | 78.7% | 37.8% | 108 | 9.90 |
| EL2 旧版 Flash（12.1% 无效句） | 72.5% | 32.9% | 102 | 20.04 |
| Embedding Top2 | 59.5% | 30.7% | 116 | — |

结论：

- 6 个配置的认可率都在 61%–68%，差距在误差内；胜负由成本决定，整库 20 条一批最便宜。
- 整库不比 Top20 差，还便宜 4–5 倍：整库 prompt 是固定前缀，能吃到缓存；Top20 每条 prompt 都不同，缓存命中为 0。
- 要求证据没有提高认可率，主要效果是让模型少给标签（覆盖率低 7–8 个百分点），成本多 10%–30%。保留证据是产品上的选择（可解释、可排查）。
- 第 1 个标签约 80% 成立，第 3 个只有 41%–63%。
- 人工标注认可率最高，但评审和标注若是同一人，这个数字偏高。

### 第 2 轮：三个维度，合并调用还是分开调用（Luna）

| 配置 | 主题 | 修辞 | 描写手法 | 元/万条 |

| 合并调用，v1 不推理 | 68.0% / 44.4%（147） | 49.3% / 76.1%（71） | 62.8% / 69.2%（43） | 5.34 |
| 合并调用，v2 不推理 | 60.2% / 44.4%（166） | 50.8% / 69.6%（63） | 61.1% / 56.4%（36） | 4.66 |
| 合并调用，v2 低档推理 | 65.1% / 42.2%（146） | 54.2% / 56.5%（48） | 79.2% / 48.7%（24） | 5.92 |
| 合并调用，v2 中档推理 | 73.2% / 44.9%（138） | 50.0% / 50.0%（46） | 76.0% / 48.7%（25） | 10.66 |

该留空时是否留空（修辞 24 条、描写手法 29 条本不该有标签的摘抄）：

| 配置 | 修辞 | 描写手法 |
| --- | ---: | ---: |
| 分开调用，v1 不推理 | 8 / 24 | 7 / 29 |
| 合并调用，v1 不推理 | 10 / 24 | 26 / 29 |
| 合并调用，v2 不推理 | 7 / 24 | 25 / 29 |
| 合并调用，v2 低档推理 | 14 / 24 | 27 / 29 |
| 合并调用，v2 中档推理 | 13 / 24 | 28 / 29 |

结论：

- 合并调用胜出。分开调用单独问一个维度时模型会硬找：描写手法 58 条里“细节描写”贴了 28 次、“心理描写”27 次，白描 8 次全错。
- 白描退役（标签库 ac1 → ac1.1）。
- prompt v2（收紧修辞、描写手法规则和四个定义）没有提高认可率，只修好了格式：重复标签 10 → 1，证据不合格 6 → 2。
- 开启推理把描写手法从约 62% 提到 76%–79%。中档比低档只在主题上更好，成本翻倍、每次请求从 19 秒变 63 秒。
- 修辞在 dev58 上始终在 50% 上下。事后看主要是判定方式造成的低估（见“怎么读这些数字”），holdout60 上是 71%–93%。

## 规模测试：1,000 条

`scripts/build-scale-set.mjs` 从 1,169 条个人摘录里按固定种子取 1,000 条（源数据里没有完全重复的句子），不按长度筛选：最短 2 字，中位数 55 字，最长 313 字。并发 8，其余设置与 holdout60 相同。**只测成本、速度和格式稳定性，没有人工判定，不说明质量。**

| | DeepSeek Flash 不推理 | Luna 低档推理 |
| --- | ---: | ---: |
| 有效条数 | 1,000 / 1,000 | 1,000 / 1,000 |
| 请求数（重试） | 50（1 次，重试后成功） | 50（0 次） |
| 总耗时 | 36 秒 | 130 秒 |
| 每次请求耗时 中位 / 最长 | 5.2 / 6.7 秒 | 18.0 / 26.5 秒 |
| 花费 | 0.097 美元 | 0.062 美元 |
| 外推 1 万条：成本 | ¥6.99 | ¥4.48 |
| 外推 1 万条：耗时（并发 8） | 约 6 分钟 | 约 22 分钟 |
| 保留的标签 | 2,783 | 3,196 |
| 本地丢弃的标签 | 116（4.0%） | 77（2.4%） |
| 其中：证据不在原文 | 34 | 47 |
| 其中：重复 | 12 | 30 |
| 其中：未知编号 | 70 | 0 |
| 平均每条（主题 / 修辞 / 描写） | 1.56 / 0.61 / 0.62 | 1.91 / 0.62 / 0.67 |
| 某维度留空的摘抄（主题 / 修辞 / 描写） | 65 / 460 / 439 | 75 / 447 / 453 |
| 三个维度全空的摘抄 | 28 | 18 |
| 用到的不同主题数（共 185） | 178 | 177 |

观察：

- 并发 8 没有触发限流。成本与 holdout60 外推的一致。
- Flash 的 70 个“未知编号”是它直接写了标签名（如“比喻”“死亡”）而不是编号。DeepSeek 走宽松 JSON 模式，没有 schema 约束。这些标签按约定被丢弃，没有修复。
- 之后（2026-11-12，负责人确认）解析器加了一条规范化：标签名与库内标签完全一致时映射回编号（同一维度、精确匹配，标记 `code_from_label`），不猜近义词。用这次 Flash 的原始输出离线重新解析：70 个里 65 个被找回并通过证据校验，3 个证据不合格，2 个是库里不存在的标签；保留的标签 2,783 → 2,848，丢弃率 4.0% → 1.8%。上表是映射前的原始结果，run 文件没有改动。holdout60 的 4 个 run 重新解析后没有任何变化，排名不受影响。
- 4 条 10 字以内的摘抄是源数据问题：微信读书导入时把划线的批注当成了划线本体。
- 证据不合格的主要原因：用省略号拼接两处（prompt 已禁止，仍会发生）；原文里有不可见字符或多余空格，模型输出时“清洗”掉了，导致对不上。
- 4 条 10 字以内的摘抄（如“喷泉”“福波斯”）两个模型都没有给任何标签。
- 修辞里比喻占一半左右（Flash 283 次、Luna 314 次）；对比 Luna 给了 102 次、Flash 64 次。描写手法里“留白”两个模型都从未使用。
- 证据超过 20 字的限制没有被本地强制：Flash 205 个、Luna 113 个超长证据被保留。

## 局限和遗留事项

- 单人盲审，样本 58 + 60 条。前三名之间的排序不可靠。
- 三档计分只适用于评审一次看到全部候选标签的盲审包（holdout60）。dev58 是增量补判的，只能用两档。
- 95% 区间只反映样本量。前三名的明显错误率区间互相重叠（3.3–10.9%、5.0–13.0%、5.1–13.7%），不能断言谁更好。
- dev58 的前两次判定把未判当作不合适，含有漏看造成的误判，没有复查修正。
- Flash 只测了不推理的版本，且只在 holdout60 上跑过完整一轮；它在 dev58 上没有可比的数字。
- 规模只实测到 1,000 条、并发 8；1 万条的数字是线性外推，更高并发下的限流没有测过。规模测试没有人工判定。
- 评审在 holdout60 备注里提出的标签库意见（未采纳，留给下一版，采纳后需另抽验证集）：
  - “欲望”应特指负面影响大的欲望，“想要”不等于欲望。
  - “未来”应是展望、畅想，不是将要发生的事。
  - 提到亲人不一定是“亲情”主题。
  - 缺少“魅力 / 吸引力”一类的主题。
  - 希望增加“场景”“角色”两个维度。
  - 缺少上下文的单句有时看不出主题，模型仍会硬贴。
