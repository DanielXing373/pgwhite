# Theme 推荐流程对比：当前开发计划

**目的：** 在同一批句子和同一份当前 Theme 库上，比较三条技术路线，选出值得继续开发的路线。

## 固定条件

- 当前唯一工作库：`research/tag-library/data/library/atomic-tag-library.v1.43.json`，共 185 个 active Theme。
- 三条路线使用相同的 Theme 表示内容：规范名、定义和 alias；不再比较 A/B/C 表示方式，也不为旧库做兼容。
- 输入都是同一批 quote 原文；输出都是当前库中的最多 5 个有序 Theme。
- 两批各 29 条、互不重叠，是样本来源，不是训练集/测试集随机切分。把它们合成一份共同对照题，并把期望标签映射到当前库。第二批曾用于整理当前库，因此分数用于开发时比较路线，不当作独立准确率结论。
- 3 条没有期望 Theme 的 quote 保留作误报检查，不计入 Recall 或 Success 的正样本分母。

## 三条路线

1. **整句直接检索**：quote 向量 → 当前 Theme 库排序。
2. **生成概念后映射**：模型先从 quote 生成概念，再映射到当前 Theme 库。
3. **召回后重排**：向量先召回候选 Theme，再由 reranker 对 quote/Theme 配对重排。

三条路线都必须跑同一份 quote fixture 和同一份当前 Theme 库。当前 runner 已覆盖路线 1；路线 2 和路线 3 尚待实现。现有 A/B/C 配置是旧的表示方式实验，不是这三条技术路线。

## 比较结果

每条路线报告 Recall@3、Recall@5、Success@3，以及每条 quote 的标注耗时、平均单条耗时和 1000 条估算耗时。耗时估算为“一次性模型／Theme 索引准备 + 平均单条耗时 × 1000”；对每条路线计入该路线完整的模型推理及映射、排序或重排耗时。当前估算按 runner 串行处理，不包含人工审核和无关的导入网络时间。

## 执行顺序

1. 将两批 quote 合成一份共同 fixture，并把人工期望标签解析到当前工作库。
2. 固定这一份库和 fixture；三条路线各自运行同一组 58 条输入。
3. 对照三项质量分数、逐句结果和耗时，决定继续开发哪条路线。
4. 如需改 Theme 库，直接更新当前工作库，再用同一套路线比较流程继续推进；不恢复旧库来做兼容性工作。
